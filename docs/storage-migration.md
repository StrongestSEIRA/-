# Issue #4 原子的スナップショット保存

## 原因と互換性

従来はGETのrevisionと後続PUTの間に別のサーバーが保存できた。プロセス内queueは別サーバーに効かず、ローカルファイルのrenameだけでも二つのプロセスが同じ版を読み取り両方成功できた。旧gatewayは更新件数ゼロでSQLSTATE 40001を発生させ、HTTP経路では再試行・タイムアウトの原因になり得た。

001は既存rootsを破壊せず、新しいCAS RPCと要求IDの記録だけを追加する。クラウドの既定はSNAPSHOT_WRITE_MODE=legacyで互換性維持。atomicは新RPCを必須とし、存在しないときに旧方式へ黙って戻さない。legacyを残した状態では旧書き込み経路の制限も残るため、本番の解決完了には承認された切り替えが必要。

## 保存契約

PUT /api/libraryは従来のbooks/revisionと、任意のIdempotency-Keyヘッダーを受け取る。新UIは一つの保存要求に同じキーを再利用する。DBが保存を確定し応答が失われても、再送は同じ成功revisionを返す。同じキーに異なる内容は409。キーを付けない旧クライアントもrevisionにより古い再送の二重適用は拒否されるが、再送成功の識別はできない。

DBはownerごとのトランザクションロックとUPDATEのrevision条件、初回INSERTの一意制約を使用する。根拠はDB内の版だけで、GETの事前照合を成功条件にしない。競合はSQL例外ではなく構造化した結果で返し、サーバーはHTTP 409へ変換する。rootsのbooks以外のデータを保持する。

要求記録はpayload全文ではなくDB内で計算したハッシュを保存する。所有者でRLSを強制し、RPCはservice_roleだけが実行可能。ユーザーにownerを指定させず、Authで検証したIDをサーバーが渡す。

UIは通信失敗時にキー・入力を保持し、新規書籍とメモのIDを保存試行間で固定する。競合時に自動で新しい版へ上書きせず、試みた内容を書き出せる。最新を読み直し手作業で差分を反映する。競合の自動マージはしていない。

## 承認後の本番適用

1. 書き込み停止時間とバックアップを承認。rootsおよび既存の全テーブル・写真の対応関係を保存し、別の隔離DBで復旧を確認する。
2. db/migrations/001_atomic_library.sqlを管理者が適用。db/schema.sqlは再実行しない。5秒のlock_timeoutでロック取得に失敗した場合は原因を確認して再計画。
3. 新RPCの実行権限とバージョン、プロジェクトのPostgreSQLバージョン、RLSを隔離環境で確認。
4. アプリを展開しSNAPSHOT_WRITE_MODE=atomicへ切り替える。旧版クライアントや複数サーバーを混在させた書き込みを監視する。
5. 409・タイムアウト・要求記録の増加を監視。保持期間を決定するまでlibrary_requestsを勝手に削除しない。長期運用では保存済み要求記録の保持・整理方針が必要。

ロールバックは書き込みを停止し、アプリをlegacyへ戻してからdb/rollback/001_atomic_library.sqlを適用する。要求ID記録を事前退避する。読書記録・rootsは削除しない。アプリのフラグ変更とSQL適用は本番承認が必要。

## ローカルと検証

localモードはディレクトリ作成の原子的ロックで別インスタンスを直列化し、fsync後にrenameする。直近256要求を同じファイルへ保存し、GETでは内部記録を返さない。プロセスがロック保持中に停止した場合は自動でロックを奪わず、保存を停止する。全利用プロセスの停止とlibrary.jsonのバックアップ・整合確認後だけ.data/library.lockを管理者が除去する。ネットワーク共有ファイルシステムを想定した分散ロックではない。

SHIORI_TEST_DATABASE_URLはループバックでshiori_testという専用DB名を含む接続先だけを許可する。テストごとに隔離DBを作成し、空DBにだけ歴史的schemaを初期化、001の適用・再適用、二つの接続と十個の並行書き込み、要求の再送・改変、匿名/認証ユーザーの拒否、承認後ロールバック時のデータ保持を検証する。HTTP応答がDBコミット後に失われたケースも二つのサーバーから試験する。本番Supabaseには接続しない。
