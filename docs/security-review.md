# Issue #3 認証レビューと段階導入計画

## 結論と適用範囲

現行のメール所有確認なしの登録は、任意のメールアドレスを名乗れる。メールは所有者確認済み識別子として信用してはいけない。本PRで本番方針・Supabase設定・既存アカウントは変更しない。推奨はメール配信を整備した後の所有確認付き登録だが、本番導入は管理者の承認が必要。

## 脅威と対策

| 脅威 | 影響 | 対策・残リスク |
|---|---|---|
| 他人のメールの先取り | なりすまし表示、正当なメール所有者の登録阻害 | emailで認可しない。現行ID別認可を維持。所有確認移行は承認待ち |
| 未検証アドレスへの再設定 | 実メール所有者が先取り利用者の読書データへ到達する可能性 | 既存の自動confirmedフラグを所有証明と解釈しない。移行時は現パスワードとメールへの新しい到達証明の両方を要求 |
| セッションを盗んだ攻撃者のパスワード変更 | アカウント固定化 | 現パスワードで再認証。検証済みJWTにある直近10分以内のOTP認証だけは再設定の証明として利用。クライアントのtypeやiatだけは信用しない |
| CSRF、ログインCSRF | 本棚変更、攻撃者のアカウントへログイン | Origin照合とcross-site Fetch Metadata拒否。メールリンクは検証したメールを表示し、明示確認とトークンに結び付いたCookieを要求 |
| refreshの再利用 | ログアウト後の短時間キャッシュ再利用 | 完了済みrefresh結果を保存しない。更新後もproviderでuser検証。ログアウトでCookieを消去 |
| 転送IP偽装 | 登録試行制限の回避 | 信頼するプロキシを明示した環境だけX-Forwarded-Forを使用。通常はsocketの接続元 |
| ユーザー間の閲覧・更新 | 書籍・メモ・写真の漏えい | user IDを検証済みAuth応答から導出。入力ownerやメールは使わない。ストレージのパスはuser IDで固定 |

SupabaseのJWT・サービスキーをログやHTMLに出さない。パスワードはSupabase Authでハッシュ管理し、本棚JSONに保存しない。メモを外部AIへ送る機能は追加しない。

## 実装済みの選択肢

`AUTH_REGISTRATION_POLICY` は `legacy`（既定・従来互換）、`verified`、`closed`。verifiedは毎回public settingsでmailer_autoconfirm=falseを確認してから通常のpublic signupを呼び、管理APIで確認済みにしない。true/欠落/不正型や、signupが予期しないセッションを返した場合は503としてCookieを発行しない。アプリの環境変数だけでは所有確認を有効にできず、Supabase側のConfirm Email有効化も承認後に必要。closedは新規登録を拒否し既存ログインを維持する。設定値が不正なら起動を拒否する。

本番の環境変数は変更していない。現パスワード入力欄を加えたため、展開時はブラウザの再読み込みを案内する。OTP由来の再設定フローは、プロバイダが検証したアクセストークンのamrとtimestampだけで判定する。実SupabaseでのAMR互換性の検証は未実施であり、隔離したテストプロジェクトで展開前に確認する。

## 推奨移行（承認が必要）

1. 既存UID・書籍・写真・現在の認証方法とバックアップを確認。自動でアカウントを削除・統合しない。
2. 配信先制限・送信上限・再設定フローを隔離プロジェクトで確認。必要なら新規登録のみclosedで停止する判断を承認してもらう。
3. SupabaseのConfirm Email有効化と、新規登録をverifiedへ変更する段階を承認。既存ユーザーのログインはそのまま維持。
4. 既存ユーザーは現在のパスワードで認証したセッション内で新しいメール所有証明を行い、別のassurance記録へ時刻・UIDを保存する設計とする。既存email_confirmed_atは管理APIで設定されているため一括で信用しない。
5. 未移行アカウントの回復でメール単独を所有証明にせず、サポートを含む回復手順・本人合意を設計してから段階移行。新旧アカウントの本棚を自動統合しない。

既存ユーザーの再確認ワークフロー・assurance保存は本PRでは未実装で、承認後の別の増分変更が必要。これを完了済みとは扱わない。

## ロールバック

アプリを直前のdevelopコミットに戻せる。登録ポリシーの切り替えをロールバックしても既存UID・読書記録を削除しない。verifiedで作成された確認待ちユーザーを一括で確認済みにしない。安全側の退避はclosedで既存ログインだけ維持する。

## 検証と制限

`npm test`、`node --test test/auth-security.test.mjs test/password.test.mjs test/registration.test.mjs`。ローカルのモック・Chromiumテストであり、本番のユーザー作成、メール送信、SQL適用、設定変更はしていない。所有確認なしの方針そのもののリスクは、コードテストが成功しても解消しない。単一プロセスの試行制限は全サーバーを横断するレート制限ではなく、プロバイダ制限と配備側の対策が必要。

## 追加レビューの残リスク

Supabase Authの公開settingsにある `mailer_autoconfirm` の契約は[公開ソース](https://github.com/supabase/auth/blob/master/internal/api/settings.go)で確認し、true/不明/途中変更のモック試験を追加した。本番設定は読み取っていない。確認設定の変更とsignupの間の競合は完全には排除できないため、不整合なセッションは返さず管理者確認を要する。自動で作成済みアカウントを削除・確認済みに変更しない。

Supabaseのログアウトはrefreshセッションを失効させるが、発行済みアクセストークンが有効期限まで使える可能性がある。Cookie消去や現パスワード再認証は、盗まれたJWTの即時失効を保証しない。短いJWT寿命や分散セッション失効照合を採用する場合は、実プロバイダでの検証・追加設計と本番承認が必要。パスワード変更後の全端末失効も実Supabaseでは未検証。

過去の会話には秘密キーが表示された画像がある。ソース/ログへ複製しておらず、そのキーの現在の有効性は照合していない。必要なローテーションは管理者の承認後に行い、無断更新しない。
