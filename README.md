# 栞 — わたしの本棚

公開HTMLを回収し、Node.jsサーバーを再実装した復旧版です。元サーバーのソースを復元したものではありません。

## 開発と起動

Node.js 24.5以降で `npm ci` の後に `npm start`。依存バージョンとチェックサムはpackage-lock.jsonに固定しています。既定のlocalモードは127.0.0.1:3000だけにバインドし、単一ユーザーのデータを `.data/library.json` に保存します。公開しないでください。テストは `npm test`。

`npm start` は環境に設定されたHTTP(S)プロキシとCA設定を使います。キーやプロキシプレースホルダーをファイルに書き出さないでください。

## 公開環境

RenderのGitHubブランチは `codex/restore-shiori`。Build Commandは `npm install`、Start Commandは `npm start`。

環境変数:

- NODE_VERSION=24.19.0
- STORAGE_MODE=supabase
- SUPABASE_URL=https://uuvdwdrmdzkxclohhihj.supabase.co
- SUPABASE_PUBLIC_KEY: Supabase Publishable key
- SUPABASE_SECRET_KEY: Supabase Secret key（サーバー専用。HTMLに配信しません）
- COOKIE_SECURE=true

`db/schema.sql` は提供されたSQLの保管用コピーです。既に初期化済みのDBには再実行しないでください。既存のshiori_gateway RPCとrootsテーブルで、認証済みユーザーID別に本棚スナップショットを保存します。既存のbooks/notesへの正規化や大規模データのページ分割は未実装です。

## ログイン：メールアドレス＋パスワード

通常のログインはパスワード方式です。ログインメールは送信しません。パスワードはHTTPSでSupabase Authへ渡し、Supabaseがbcryptとランダムなsaltでハッシュとして管理します。アプリのソース、ログ、本棚データ、バックアップにパスワードを保存しません。メールアドレスはSupabase Authのアカウント情報として保存します（独自のフィールド暗号化は行いません）。実利用者のメールアドレスやパスワードをソースに埋め込みません。

### 初回

- 新しいメールアドレス: 「初めての方はこちら」から登録。メール確認は維持します。パスワードは12文字以上、UTF-8で72バイト以内。
- 以前メールリンクで使っていたアカウント: 「パスワードを設定・再設定」から、一度だけ設定メールを送り、最新リンクを開き、アカウント確認後にパスワードを設定します。
- 初回確認・パスワード再設定メールには標準配信枠（現在プロジェクト全体で2通/時）が適用されます。送信枠の回復はコード修正では早められません。メール確認を無効化したり、管理APIで実利用者のパスワードを認証なしに設定したりはしません。

SupabaseのAuthentication → URL Configuration:

- Site URL: `https://book-s-marker.onrender.com/`
- Redirect URLs: `https://book-s-marker.onrender.com/**`

カスタムSMTPやメールテンプレートの変更は必須ではありません。継続的な新規登録・再設定メールの送信が必要になった場合は配信サービスの設定が必要です。

### ログイン保持とログアウト

アクセストークンとリフレッシュトークンをHttpOnly・SameSite Cookieに保存します。公開環境はSecure付きです。リフレッシュトークンは/api/だけに送られ、JavaScript・localStorageやソースコードから参照できません。セッションが切れた際はSupabaseで更新し、通常の再ログインにメールは不要です。リフレッシュCookieの有効期間は最大30日で、Supabase側のセッション失効設定が優先されます。

「ログアウト」はSupabaseの当該セッションを失効させ、アプリのCookieを削除します。パスワードの設定・変更APIは認証済みユーザーのトークンだけで実行し、別のメールアドレスを指定した書き換えは行いません。

登録確認・再設定メールのリンクは、開いたブラウザでトークンを検証し、表示されたメールアドレスを明示的に確認してからセッションに変換します。再設定リンクではパスワード入力画面を開きます。旧画面のメールのみのログイン要求は410で停止し、再読み込みを案内します。

## 検証

`npm test` はローカル永続化、更新競合、認証境界、新しいブラウザでのメールリンク確認、キャンセル、不正トークン、パスワードログイン、セッション更新、失効済みリフレッシュ、パスワード変更、ログアウト、初回メール確認、送信制限を確認します。

Supabase接続と書き込みは `node --use-env-proxy scripts/check-supabase.mjs --write-check` で検証できます。一時所有者の本棚を作成し、読み戻し・更新後に削除します。監査履歴は残ります。キーの値は出力しません。

実Supabaseの管理APIでメール送信なしの一時テストユーザーと標準メールリンクを生成し、検証用リンクを開いたときのリダイレクトから、ブラウザ側ヘルパー、サーバー側の確認処理、認証後のアカウント取得まで成功しました。送信元Cookieなしで検証し、テストユーザーは削除済みです。コード入力によるログインと認証後の本棚保存・読み戻しも検証済みです。利用者の実端末からのメール受信・画面操作は別途確認が必要です。

## 残る制限

書籍検索は国立国会図書館サーチのOpenSearch APIを使用します。検索対象に収録されていない本もあり、候補がないことは書籍が存在しないという意味ではありません。外部APIの停止・エラーを「該当なし」に置き換えません。旧ChatGPTログインはSupabaseメール・パスワード認証へ変更しています。

DBに意図的に古いversionを送るとSQLSTATE 40001応答がタイムアウトする問題が、この接続経路でNodeとcurlの両方に再現しました。通常保存は書き込み前にrevisionを確認して409を返しますが、複数サーバーから同時更新した際のDB競合応答は未解決です。タイムアウト時は自動再送せず、再読み込みして保存状況を確認してください。

## メール送信制限の診断

公式資料とSupabase Authの実装を確認しました。同じ `over_email_send_rate_limit` コードが、配信枠の上限と同じユーザーへの短時間再送の両方に使われます。エラーコードだけでプロジェクトの時間上限と断定しません。

- 本文が `email rate limit exceeded` の場合は、メール配信枠の制限として表示。
- `after N seconds` の再送間隔エラーは、その待ち秒数を反映。
- Retry-Afterが提供された場合は、整数秒またはHTTP日時から待ち時間を取得。
- 不明な429は不明のまま表示し、60秒で解除されるとは案内しません。
- 429で再試行時刻が分からないときは送信ボタンを停止し、繰り返しの送信を促しません。自動再送は行いません。

過去のAPI応答はエラー種別を破棄していたため、利用者が遭遇した当該429の詳細は遡って確定できません。プロジェクトの実設定・履歴には別途管理画面での確認が必要です。修正検証ではメールを送らず、配信枠・再送間隔・IP制限・詳細不明の429とRetry-Afterをモックで検証しました。

参照: https://supabase.com/docs/guides/auth/rate-limits と https://supabase.com/docs/guides/auth/auth-smtp 。確認時の公式共有設定 https://github.com/supabase/supabase/blob/master/packages/shared-data/config.ts では `auth.rate_limits.email.inbuilt_smtp_per_hour.value` は2です。これは既定値で、プロジェクトの現在値を直接取得したものではありません。

## パスワード方式の実接続検証

メールを実送信せず、ランダムな一時テストアカウントをSupabase管理APIで作成して確認しました。実利用者の登録フローのメール確認は変更していません。

- パスワードログインと認証後の本棚保存。
- パスワードやメール送信なしのリフレッシュ。
- パスワード変更、古いパスワードの拒否、新しいパスワードの受け入れ。
- ログアウト後のリフレッシュ拒否。
- パスワード未設定のアカウントから、再設定リンクの検証、パスワード設定、パスワードログインまで。

検証用アカウントと本棚は削除済みです（本棚の監査履歴は保持）。テストパスワードやトークンは出力・ファイル保存していません。実ブラウザの画面操作と利用者による初回設定は別途確認が必要です。

Supabaseのパスワード保存方式: https://supabase.com/docs/guides/auth/password-security

## 既存アドレスでの再登録について

Supabase Authは、確認済みの既存アドレスへの新規登録要求に対し、アカウント有無の漏えいを避けるため、メールを送信せずに匿名化した正常応答を返す場合があります。再登録要求で既存のパスワードは変更されません。

アプリはセッションが発行されない登録応答を `signupRequested` として返し、「確認メールを送りました」と断言しません。既存・新規で異なるアカウント照会APIを呼んだり、管理APIでパスワードを書き換えたりはしません。新規登録画面からも「パスワードを設定・再設定」に進めます。設定依頼の応答も `recoveryRequested` とし、メールの到達を保証する表現を避けます。

登録先が標準メールの送信許可対象でない場合の `email_address_not_authorized` は、宛先アドレスをエラーへ出さず、メール配信設定が必要であることを表示します。登録・回復の送信テストはモックで実施しており、利用者宛ての追加メールは送信していません。

## 写真から直接登録

「本を登録する」でカメラ撮影または写真選択を行い、そのまま保存できます。タイトル未入力なら「タイトル未入力」の本として写真を保存し、後から編集できます。OCR・検索は必須ではありません。書籍情報の検索は任意で、候補選択や検索失敗後も、写真と入力途中の内容を保持します。自動書誌取得は新しい本では初期値OFFです。

写真はブラウザでJPEG・300KB以下に変換し、認証済みのAPIから非公開のSupabase Storageバケット `shiori-covers` に保存します。初回アップロード時に非公開バケットを準備し、公開設定のバケットには保存しません。アップロード・取得の所有者IDにはSupabaseで検証したユーザーIDを使います。写真は本棚のJSONスナップショットとは別保存で、写真数に比例して全件更新リクエストの容量が増える問題を避けます。localモードは.data/coversに保存します。

写真の書き出しは画像データをJSONへ埋め込み、復元時に本人のストレージへ再アップロードします。他のアカウントの画像URLをそのまま共有しません。書き出し中に画像を取得できない場合は不完全なバックアップを黙って作りません。監査履歴や復元との整合のため、アップロード済み画像を本の削除時に自動削除する機能はまだありません。保存失敗後の未参照画像を含むストレージの整理は今後の課題です。

写真の撮影・選択、プレビュー、タイトルなし保存、再読み込み、後からのタイトル編集、画像入りJSONの書き出しと復元をモバイル幅のChromiumで検証しました。タイトル検索の候補選択、検索サービス停止時のエラー表示、保存前の写真を失わず編集へ戻る動作も実ブラウザで確認しています。ブラウザテストには `/usr/bin/chromium` またはCHROMIUM_PATHで指定したChromiumが必要です。playwright-coreは開発依存のみです。

実Supabaseの非公開バケットに検証用写真を保存・取得し、別の所有者からの取得が拒否されることを確認しました。検証用写真は削除済みです。バケットは非公開のままです。追加のサービス登録や有料プランへの変更はしていません。既存の無料プランの容量制限が適用されます。

## 国立国会図書館サーチ接続

`https://ndlsearch.ndl.go.jp/api/opensearch` に書名・著者またはISBNで問い合わせます。利用者の写真・認証キーは送りません。複数の候補は選択式で、版を決めつけません。写真や手入力は検索の応答待ちにせず保存できます。

現在の開発環境では `ndlsearch.ndl.go.jp` と公開アプリ `book-s-marker.onrender.com` の通信許可を下書きに保存しています。設定の保存・公開が反映されるまで、この環境から外部検索と公開アプリへの実接続は未検証です。XML応答の解析とブラウザの候補選択はフィクスチャで検証しており、これをライブ検索の成功とは扱いません。
